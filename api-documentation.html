Quick start

The fastest path to a working integration: get a key pair from a staff member, then create your first ticket.

1. Get an API key/secret pair. A staff member generates one from wp-admin -> Affiniti Support -> API Keys. The secret is shown once at creation - store it immediately, it cannot be retrieved again. Up to 2 keys can exist at a time; revoke one to make room for another.

2. Create the ticket. No product lookup needed - a ticket only needs the customer's contact details and the problem.

curl 
curl -X POST "https://your-site.com/wp-json/wpsd/v1/tickets" \
  -H "Content-Type: application/json" \
  -H "X-WPSD-API-Key: wpsd_xxxxxxxxxxxxxxxx" \
  -H "X-WPSD-API-Secret: wpss_xxxxxxxxxxxxxxxxxxxxxxxxxxxx" \
  -d '{
    "customer_name": "Rahim Uddin",
    "mobile": "01712345678",
    "address": "House 5, Road 2, Dhanmondi, Dhaka",
    "warranty_id": "WR-88213",
    "problem_description": "Fridge is not cooling since yesterday"
  }'

A successful call returns 201 with the new ticket, including its human-readable ticket_number (e.g. TKT-2026-00042) - give that to your customer.

Authentication

The API recognizes three separate callers. Pick the one that matches what you're building - they are never interchangeable.

CallerMechanismUse for
External tool this doc X-WPSD-API-Key + X-WPSD-API-Secret headers Any integration outside WordPress itself - CRMs, call-center tools, Postman, scripts.
Staff (admin app) WordPress cookie + X-WP-Nonce The plugin's own React admin screen. Not usable outside a logged-in browser session.
Guest web form wpsd_nonce body/query param The plugin's own public ticket-submission shortcode. Single-page-load lifetime, not for external use.

Sending the API key

Every authenticated request carries two headers:

headers 
X-WPSD-API-Key: wpsd_43844b7156c95fd3cae0095a320efbbe
X-WPSD-API-Secret: wpss_7bd505671070f65858f79451108408d7188754852772ef916ddba21cfd2889
!

HTTPS is required for API-key requests on any real domain. It's automatically relaxed for local dev hosts - localhost, 127.0.0.1, and any .local/.test domain - so you can build and test from Postman without a certificate.

Scopes

Each key is created with one scope, set by the staff member who generated it. It governs read/list access only - every key can always create tickets.

Optional: request signing (HMAC)

For callers that want replay protection on top of the key/secret, add two more headers. When either is present, both are checked:

HeaderValue
X-WPSD-TimestampCurrent Unix time (seconds). Must be within 5 minutes of the server clock.
X-WPSD-Signaturehex(HMAC-SHA256(timestamp + "." + raw_request_body, api_secret))
node.js - signing example 
const crypto = require('crypto');
const timestamp = Math.floor(Date.now() / 1000).toString();
const body = JSON.stringify(payload);
const signature = crypto
  .createHmac('sha256', apiSecret)
  .update(`${timestamp}.${body}`)
  .digest('hex');
// send X-WPSD-Timestamp: timestamp, X-WPSD-Signature: signature

Postman & Insomnia

One thing trips up almost every integrator on their first request - read this before you open a support thread about it.

X

Do not use the "Basic Auth" tab in your HTTP client. WordPress core intercepts any Authorization: Basic header before your request reaches this plugin at all, and rejects it unless the username happens to match a real WordPress login with a matching Application Password. It has nothing to do with your API key.

Correct setup in Postman:

  1. Authorization tab -> Type -> No Auth.
  2. Headers tab -> add X-WPSD-API-Key and X-WPSD-API-Secret as plain header rows.
  3. For POST/PATCH requests, set Content-Type: application/json and put the JSON body under Body -> raw -> JSON.

"No Auth" doesn't mean unauthenticated - it just tells Postman not to auto-generate its own Authorization header. Your two X-WPSD-* headers are the real credentials, checked entirely by this plugin.

Response envelope

Every response - success or failure - is shaped the same way, on every endpoint.

200 / 201 - success 
{
  "success": true,
  "data": { ... },
  "error": null
}
4xx / 5xx - failure 
{
  "success": false,
  "data": null,
  "error": {
    "code": "wpsd_not_found",
    "message": "Ticket not found."
  }
}

Field-level validation failures put a fields object under data instead of null:

validation error 
{
  "success": false,
  "data": { "fields": { "mobile": "Mobile number must be a valid Bangladeshi number (e.g. 01712345678)." } },
  "error": { "code": "wpsd_validation_failed", "message": "Validation failed." }
}
!

Known quirk: wpsd_validation_failed responses currently arrive with HTTP status 200 instead of 400, even though success is correctly false. Always branch on the success field, not the HTTP status code alone - this is on the fix list but not yet shipped.

Error codes

wpsd_validation_failed200*One or more fields failed validation - see data.fields. *See quirk above.
wpsd_bad_nonce403Guest/web create was missing or had an invalid wpsd_nonce.
wpsd_duplicate_ticket409Same mobile + same problem description submitted again within 10 minutes.
wpsd_rate_limited429Too many requests - see Retry-After header.
wpsd_unauthorized401Missing, unknown, or incorrect API key/secret.
wpsd_https_required403API-key request over plain HTTP on a non-local domain.
wpsd_forbidden401/403Authenticated, but this scope/capability can't do that.
wpsd_owner_required403Guest ticket read with no mobile/phone provided to prove ownership.
wpsd_not_found404No ticket / resource with that identifier.
wpsd_limit_reached409The API-client cap (2 by default) is already full.
wpsd_in_use409Admin tried to delete a lookup row a ticket still references.

Note the wpsd_duplicate_ticket guard: submitting the same mobile + problem_description again within 10 minutes returns 409 instead of creating a second ticket - useful, but don't mistake it for a bug if you're testing with a fixed payload.

GET/tickets/{ticket_number}?mobile=

Look up a ticket by its public number. A customer-facing "check my ticket status" endpoint.

API key (create_and_read+)Staff cookieGuest + mobile

With an API key of scope create_and_read or full, mobile isn't required - the key itself is the authorization. Without a key, the caller must supply the mobile the ticket was created with; a mismatch returns a deliberately generic 403 so ticket numbers can't be brute-forced against arbitrary phone numbers.

curl 
curl "https://your-site.com/wp-json/wpsd/v1/tickets/TKT-2026-00042" \
  -H "X-WPSD-API-Key: wpsd_xxxxxxxxxxxxxxxx" \
  -H "X-WPSD-API-Secret: wpss_xxxxxxxxxxxxxxxxxxxxxxxxxxxx"
GET/tickets?id=&phone_number=

The same guest lookup as above, but keyed by the numeric ticket id and parameter name phone_number instead. No credentials needed - ownership is proven by the phone match.

None (phone match required)
curl 
curl "https://your-site.com/wp-json/wpsd/v1/tickets?id=42&phone_number=01712345678"

A wrong phone_number returns 403; a nonexistent id returns 404. Both are deliberately terse to avoid id enumeration.

/lookups/products | /districts | /thanas | /routes | /service-centers | /problem-types

Legacy reference data - WooCommerce product search plus Bangladesh administrative-area and problem-category lookups. These predate the current ticket form and are no longer required for ticket creation - product_id/district_id/thana_id/route_id/service_center_id are accepted for backward compatibility but always read back as 0 on new tickets. Left here for completeness; safe to ignore in a new integration.
